# 渠道历史恢复与来源隔离审阅

基线 a125092。由实现者进行源码审阅、故障用例和编译版验证，没有委派其他 Agent。

## 实现结论

- 安装渠道与默认 channels 包均留存原字节。默认包完整嵌入 CLI，dist 安装包使用相同内容；channel ABI/宿主批准独立于 domain ABI，已有领域批准不被改写。
- 注册表区分当前默认和精确渠道代际。显式原 provenance 只能解析原实现，裸 descriptor 不能回退到历史；历史只加载被引用的渠道贡献，不启动旧 application/interface。历史贡献依赖直接拒绝，当前渠道的适配器依赖也不能由 recovery-only 领域实现满足。
- 来源固定记录迁入宿主私有命名空间，保存原 descriptor 和 Source transport identity。一次迁移在升级应用 import 前完成，需旧渠道绑定和原 Source 注册事实；不完整记录不自动授予新绑定。迁移后应用伪造旧行不能改变宿主选择。
- Source 配置变化在调用渠道之前校验，且不为不匹配的 Source 初始化历史代际。actor/controller 和任务授权使用当前宿主配置，恢复旧渠道不恢复被撤销的业务权限。归档身份、原安装选择、trust、阻止指纹和批准均沿用现有校验。
- 渠道的旧 namespace/目录由持久 owner 占有，新代际使用含指纹的独立状态空间。历史数据不能确定原 owner 时明确阻塞；不让新代码先启动而误占原状态。游标和 Outbox 的应用记录保留原键。
- 单 Source 失败不阻止核心和其他来源。状态暴露 ready:false、available:false 和具体错误，入站返回可重试的 503、不确认事件；不可用来源的 pending 事件、通知和 watcher 工单不被改成另一份任务。接单与发送按可用来源查询，避免旧来源积压占据全局前缀，饿死健康来源。
- 停止仍先取消并排空各代连接，再清理应用状态租约、Worker、包快照和数据库；已观察到的发送结果可在排空期记账。unknown 不因为代码恢复就变成 pending，不自动重发。

## 审阅中处理

1. 原来只比较当前渠道与旧 descriptor，无法解析旧实现。改为分离默认索引与代际索引，依赖检查仍只使用当前贡献，不隐式换依赖。
2. 不能只改 registry：Source 身份和初始化引用也必须使用原绑定。宿主先迁移/读取绑定，再计算 channel refs，应用仅按 Source ID 取固定 descriptor。
3. 历史与当前渠道共享原状态 namespace 会让新代码覆盖旧游标和回执。新增 owner 事实及代际空间，测试同命令 ID、不同代际各自保存回执和计数。
4. 只有 Code 恢复仍不足以恢复整个渠道业务。实际验证同时覆盖签名入站、模型问答、丢确认的出站通知、原 ticket/Run 和新来源。
5. 缺少旧包不应使整个 Runtime 退出。来源失败隔离到 ready/available 状态，其他来源继续；同时修正 pending 前缀选择，否则 300 条不可用来源积压仍能阻塞健康来源。
6. 原 builtin domain 批准协议保持不变，避免新增渠道 ABI 时使刚交付的 Coding 任务全部失去批准。渠道包必须有自己的批准，metadata 标签不能替代它。

## 验证内容

自动化测试覆盖新旧渠道代码/状态分流、原 poll 状态、无历史应用 import、服务/依赖限制、连接取消排空、禁用/撤权/阻止指纹/缺包/损坏、builtin channel 专属批准、旧来源一次迁移、迁移后伪造历史、不完整注册拒绝和传输配置不匹配。

真实守护进程测试独立安装完整渠道包，使用本地签名 webhook 自动提问。接收方看到了问题但返回无效确认，通知变为 unknown；升级包并重新信任后，旧来源继续用旧实现、新来源用新实现，原问题和通知 ID 保持，unknown 不重发。回答完成原 Run，撤销 actor 后的新请求 rejected，不增加模型请求或任务。

macOS/Linux 双编译版探针同时更换 Coding、channels 和宿主构建身份：接单去重→真实 read→自动问题通知→停止 A→启动 B→回答→原代码完成→新 Source 使用新渠道/新 Coding；合计 4 次模型请求、1 次 read、2 个 Run。再次重启不重复任务/未知通知。随后在停止状态删除测试用旧渠道归档，验证仅旧 Source unavailable，健康来源和核心仍可启动。没有实际收费模型、外部 MCP 或社交渠道。

最终本地验证：macOS 1062 pass、2 skip、0 fail，4248 次断言；Linux 1057 pass、7 skip、0 fail，4230 次断言。两端各运行 159 个文件、1064 个测试，均开启 `TNB_REQUIRE_NATIVE_SANDBOX=1`；类型检查、编译和上述双版本编译探针均通过。平台专属测试按运行平台跳过。

本地证据：`/Volumes/data/tnb-review-2026-11-05/channel-generations/`。新增真实升级测试跨多个轮询和三次 owner 启停，单例超时设为 20 秒；初始默认 5 秒不足导致过超时，没有以此放宽生产网络或操作期限。主分支 CI 另外执行 macOS/Linux 全量测试及 Windows 聚焦测试。

## 限制

旧版内置渠道只有全宿主指纹、没有原可执行包，不能自动重建；原来源明确不可用，不能偷偷接管。没有恢复历史应用/交互或历史渠道依赖闭包，不提供热替换、跨 ABI 迁移或进程隔离。独立安装的协作应用需更新到使用 channel(sourceId) 的实现。

Source 绑定在移除配置、禁用或 Run 终态后仍保留引用。当前未提供退休 Source 并删除其历史绑定的操作，不能把 Run prune 当成渠道释放。数据库备份仍不包括归档，灾备需额外保存代码、安装信任与宿主批准。Windows 验证可移植加载/状态/权限/迁移部分，不承诺完整 owner 执行恢复。
