# 插件引用清单和回收准入审阅

审阅对象为[规格](../specs/2026-11-05-plugin-reference-inventory.md)、[使用指南](../../guides/plugin-references.md)及实际宿主实现。本轮由实现者审阅，未委派其他 Agent。

## 问题与实现

原 `loadHostPlugins` 只以 `generationReferences` 是否存在决定是否回收历史目录；宿主漏传独立的 `channelReferences` 时，可能误删旧 Source 仍固定的渠道包。现在领域与渠道两类清单都明确提供才回收；省略表示未知，纯领域宿主明确传渠道空数组。默认产品组合与 SDK 原本已提供两类清单，继续自动收集。没有改动持久绑定或数据库版本。

引用报告按包名、版本和指纹分组，列出根配置、子任务覆盖和渠道绑定。终态 Run 和停用 Source 保留代码但不要求加载；其他引用需要加载时合并为该代有加载需求。内存实现严格匹配全部身份字段，查询返回副本，不暴露可修改宿主状态的对象。

产品从当前 owner 的 RuntimeStore 读取，沿用该 owner 已生效的协作配置。测试在启动后新增绑定、修改磁盘配置，确认前者立即可见，后者不会冒充当前策略。SDK 同样每次重读存储；直接宿主需每次提供当前完整清单。旧 inventory 数组与启动计数语义保留。

回收结果明确属于启动阶段，区分禁用原因、完成和失败。查询没有异步切换点、状态写入、插件 import、网络连接或回收行为。prune 后报告可以立即移除已释放引用，但宿主仍持有的历史实现与归档等到后续生命周期处理，不在查询中删除。回收失败不承诺回滚此前成功删除的无引用目录。

## 验证

专项覆盖混合贡献引用、精确身份、返回副本、遗漏任一/全部清单、停用绑定、终态与子任务覆盖、实时 prune、无历史根及回收失败，以及 API/CLI/对话命令的一致性。旧渠道归档与遗留暂存目录在未知清单启动时均保持原样；完整清单启动只清理允许的无引用内容。

macOS 设置 `TNB_REQUIRE_NATIVE_SANDBOX=1` 的完整回归为 1192 项通过、3 项跳过、0 失败，171 个文件、4986 次断言。类型检查、构建与 `git diff --check` 通过。编译版 CLI 在独立临时配置目录完成启动、引用查询、旧列表查询和停止；停止后查询报错，未自动启动 owner。测试未调用付费模型或外部业务服务。

Windows 定向验证列表加入引用投影单元测试，既有领域/内置/渠道代际集成测试继续执行；macOS/Linux 执行全套。远端结果以该提交的工作流为准，Windows 不因此获得完整持久 owner 执行承诺。

本机验证日志位于 `/Volumes/data/tnb-review-2026-11-05/plugin-references-{full,typecheck,build}.log`。

## 未交付边界

报告解释持久保留与加载需求，不检查归档字节完整性、账户、信任、连接健康或完整恢复能力。它不枚举任意插件私有状态，也不能证明宿主调用者自行提供的清单确实完整。Source 配置被移除仍保留原绑定，没有开放直接删除或强制退休入口。Source 退休仍需宿主业务事实预检、墓碑、兼容屏障和备份引用一致性；完整恢复预检、统一 MCP/Channel 凭据与预算、Run/call 服务作用域继续留在后续规范。
